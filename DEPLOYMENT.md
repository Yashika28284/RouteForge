# Deploying RouteForge — Neon + Upstash + Render + Vercel

This maps the four services onto RouteForge's five pieces:

| Piece                          | Where           |
|---------------------------------|-----------------|
| PostgreSQL                      | Neon            |
| Redis                           | Upstash         |
| Fastify backend (public)        | Render — Web Service |
| Python/OR-Tools optimize-service (internal) | Render — Private Service |
| React/Vite frontend             | Vercel          |

Backend and optimize-service both need a real, always-on server process (and
OR-Tools needs a real Python runtime), so they go on Render. The frontend is
a static build, so it goes on Vercel.

Code changes already made for this:

- Postgres pool now accepts a `DATABASE_URL` connection string with **full
  SSL certificate verification** by default (Neon's certs are publicly
  trusted, so this works without extra config — see the Security section
  below for the escape hatch and why it's off by default).
- CORS now checks against an explicit allowlist (comma-separated origins,
  plus an optional scoped regex for preview-deploy URLs) instead of a
  single hardcoded origin, and no longer requests `credentials: true`
  (the API is Bearer-token auth only, no cookies — that flag only widened
  the attack surface for no benefit).
- Added `@fastify/helmet` for security headers (CSP, `X-Content-Type-Options`,
  etc.) and a tighter, separate rate limit on `/api/auth/*` (10/min vs the
  API-wide 100/min) to slow down credential stuffing.
- Both backend and optimize-service Dockerfiles now run as a non-root user.
- Redis needed no changes — node-redis auto-negotiates TLS for `rediss://`
  URLs like Upstash's.

All of this is covered by tests (29/29 pass, including new CORS unit
tests) and `tsc --noEmit`/`eslint` are clean.

## 0. Push to GitHub

Render and Vercel both deploy from a git repo.

```bash
cd routeforge
git init
git add .
git commit -m "Initial commit"
gh repo create routeforge --private --source=. --push
# or: create an empty repo on github.com, then
#   git remote add origin <your-repo-url> && git push -u origin main
```

## 1. Neon (Postgres)

1. [neon.tech](https://neon.tech) → New Project → any region close to your
   Render region.
2. On the project dashboard, **Connect** → copy the connection string
   ("Pooled connection" is fine). It looks like:
   `postgresql://user:password@ep-xxxx-pooler.region.aws.neon.tech/routeforge?sslmode=require`
3. Save it — this becomes `DATABASE_URL` in step 3.

Schema is applied automatically on deploy (see the backend's
`preDeployCommand` in `render.yaml`), so no manual migration step is needed.

## 2. Upstash (Redis)

1. [upstash.com](https://upstash.com) → Create Database → Redis, any region
   close to Render.
2. On the database page, copy the **TLS** connection string — it starts with
   `rediss://` (note the double-s: TLS). This becomes `REDIS_URL`.

Redis is a cache-aside layer here (matrix + geocode caching) — if it's ever
briefly unreachable the app degrades gracefully rather than failing
requests, so there's no strict ordering requirement between this and the
other steps.

## 3. Render (backend + optimize-service)

The repo includes `render.yaml`, so both services deploy together as a
Blueprint:

1. [render.com](https://dashboard.render.com) → New → **Blueprint** → connect
   your GitHub repo → Render reads `render.yaml` and proposes both services.
2. Before applying, you'll be prompted for the env vars marked `sync: false`:
   - `routeforge-backend` → `DATABASE_URL` (from Neon, step 1)
   - `routeforge-backend` → `REDIS_URL` (from Upstash, step 2)
   - `routeforge-backend` → `CORS_ORIGIN` — leave as `http://localhost:5173`
     for now; you'll update it to the real Vercel URL in step 5.
   - `routeforge-backend` → `CORS_ORIGIN_REGEX` — optional, leave blank
     unless you specifically want Vercel *preview* deploy URLs (a new
     random subdomain per branch/PR) to also work against this backend.
     See the Security section below before setting it.
   - `JWT_SECRET` is auto-generated by the blueprint (`generateValue: true`)
     — no action needed.
3. Apply. Render builds both Dockerfiles, runs the Postgres migration as a
   pre-deploy step on the backend, then starts both services.
   `routeforge-optimize-service` is a **private service** — no public URL,
   only reachable from the backend over Render's internal network — which is
   correct, since nothing external should call the solver directly.
4. Once live, copy the backend's public URL (something like
   `https://routeforge-backend.onrender.com`) — you'll need it in step 4.

If you'd rather click through the dashboard instead of using the blueprint,
create two services manually: a **Private Service** from
`optimize-service/Dockerfile` on port 8000, and a **Web Service** from
`backend/Dockerfile`, with `OPTIMIZE_SERVICE_URL` on the backend pointing at
`http://<optimize-service-name>:8000`.

## 4. Vercel (frontend)

1. [vercel.com](https://vercel.com) → Add New → Project → import the repo.
2. Set **Root Directory** to `frontend`. Vercel auto-detects the Vite
   framework preset; the included `frontend/vercel.json` handles SPA
   client-side routing (react-router) so deep links/refreshes don't 404.
3. Add an environment variable:
   `VITE_API_BASE_URL = https://routeforge-backend.onrender.com/api`
   (your real Render backend URL from step 3, with `/api` appended).
4. Deploy. Copy the resulting Vercel URL (e.g.
   `https://routeforge.vercel.app`).

## 5. Close the loop: CORS

Go back to Render → `routeforge-backend` → Environment → set `CORS_ORIGIN`
to your real Vercel URL from step 4 (e.g. `https://routeforge.vercel.app`,
no trailing slash). Save — Render redeploys automatically.

## 6. Verify

```bash
curl https://routeforge-backend.onrender.com/api/health
curl https://routeforge-backend.onrender.com/api/health/ready   # checks postgres + redis
```

Then open the Vercel URL, register a user, load the demo route, and hit
Optimize — this exercises the full chain: Vercel → Render backend → Neon +
Upstash → Render optimize-service → OSRM's public demo server.

## Security

What's already handled for you:

- **Transport**: Vercel and Render both auto-provision TLS, so the frontend
  and backend are HTTPS-only with no extra config.
- **Database**: `DATABASE_URL` connects to Neon with full certificate
  verification on by default (not just "encrypted but unauthenticated").
  Don't set `POSTGRES_SSL_INSECURE=true` — it exists only for providers
  with a self-signed cert Node can't verify, which Neon isn't.
- **CORS**: locked to an explicit allowlist (`CORS_ORIGIN`), not a
  wildcard. Since auth is Bearer-token-only, `credentials` is off, which
  keeps the CORS policy as tight as it can be.
- **Secrets**: `JWT_SECRET` is auto-generated by the Render blueprint —
  you never type or see a weak one. `DATABASE_URL`/`REDIS_URL` are
  `sync: false`, so they're entered once in the Render dashboard and never
  committed to git (`.env` is gitignored too).
- **Rate limiting**: 100 req/min API-wide, 10 req/min specifically on
  `/api/auth/*` to slow down brute-force login/registration attempts.
- **Security headers**: `@fastify/helmet` adds a locked-down CSP and the
  standard hardening headers (this is a JSON API with no HTML views of its
  own, so there's no reason to loosen the CSP).
- **Containers**: both the backend and optimize-service Docker images run
  as a non-root user.
- **Error responses**: the existing centralized error handler never leaks
  stack traces (unchanged from before, just worth knowing it's there).

Things worth doing yourself:

- **Rotate `JWT_SECRET` if it's ever exposed** (e.g. pasted somewhere
  public) — Render will regenerate on redeploy if you delete and re-add the
  var, and doing so invalidates all existing logged-in sessions, which is
  expected.
- **`CORS_ORIGIN_REGEX` is opt-in and scoped on purpose** — the example in
  `.env.example` matches only `routeforge-git-*-yourteam.vercel.app`, not
  every `*.vercel.app` site. If you turn it on, keep it scoped to your own
  project's preview pattern (check your team slug in the Vercel dashboard).
- **`npm audit`** currently flags a few advisories in the pinned Fastify 4.x
  line (DoS/header-parsing issues, fixed in Fastify 5). None are exploitable
  through this app's usage, but if you have time before a real (non-demo)
  launch, upgrading to Fastify 5 is a reasonable follow-up — it's a breaking
  change so it's out of scope for this deploy pass.
- **The JWT lives in `localStorage`** (pre-existing design, not something I
  changed) — standard for an app like this, but it does mean an XSS bug
  could steal a token. The CSP added above is a meaningful mitigation; if
  this ever handles real user data beyond a portfolio demo, moving to an
  httpOnly cookie would be the next step up.
- **Neon/Upstash dashboards** — both support rotating credentials and (on
  paid tiers) IP allowlisting if you want to further restrict access beyond
  the connection-string secret.

## Notes / gotchas

- **Render free/starter services spin down when idle** and take ~30–60s to
  wake on the next request — the first optimize call after inactivity will
  be slow. Fine for a portfolio demo; upgrade the plan if you need it always
  warm.
- **OSRM/Nominatim** are the public demo servers (per the original design —
  self-hosting was explicitly out of scope for v1). They're rate-limited and
  not meant for heavy production traffic, which is fine for a demo but worth
  knowing about.
- **Neon's pooled connection string** is recommended over the direct one
  since Render's free/starter plans can otherwise exhaust Neon's connection
  limit under load.
- If you rotate `JWT_SECRET` on Render, all existing logged-in sessions are
  invalidated (expected — it's what the secret is for).

## Troubleshooting

- **Frontend loads but every request fails / console shows a CORS error** —
  `CORS_ORIGIN` on the backend doesn't exactly match your Vercel URL
  (check for a trailing slash, or `http` vs `https`). Update it and Render
  will auto-redeploy.
- **`/api/health/ready` returns `postgres: false`** — usually means
  `DATABASE_URL` wasn't pasted correctly, or you're missing
  `POSTGRES_SSL=true`. Check the Render service logs for the actual
  connection error.
- **`/api/health/ready` returns `redis: false`** — check the Upstash URL
  uses `rediss://` (TLS), not `redis://`. This one is non-fatal either way
  (caching just silently disables), so the app still works, just slower.
- **Optimize requests fail with `OPTIMIZE_SERVICE_UNAVAILABLE`** — the
  `routeforge-optimize-service` private service either isn't deployed yet
  or is still spinning up (cold start). Check its logs in the Render
  dashboard.
- **First request after a while is slow (~30-60s)** — expected on
  Render's free/starter plan; see the gotcha below.
