# Deploying RouteForge — Neon + Upstash + Render + Vercel

This maps the four services onto RouteForge's five pieces:

| Piece                          | Where           |
|---------------------------------|-----------------|
| PostgreSQL                      | Neon            |
| Redis                           | Upstash         |
| Fastify backend (public)        | Render — Web Service |
| Python/OR-Tools optimize-service (internal) | Render — Private Service |
| React/Vite frontend             | Vercel          |

Backend and optimize-service both need a real, always-on server process (and
OR-Tools needs a real Python runtime), so they go on Render. The frontend is
a static build, so it goes on Vercel.

Code changes already made for this: the Postgres pool now accepts a
`DATABASE_URL` connection string with SSL (Neon requires SSL; the original
code only supported discrete unencrypted `POSTGRES_*` vars). No other code
changes were needed — Redis already just takes a URL, and node-redis
auto-negotiates TLS for `rediss://` URLs like Upstash's.

## 0. Push to GitHub

Render and Vercel both deploy from a git repo.

```bash
cd routeforge
git init
git add .
git commit -m "Initial commit"
gh repo create routeforge --private --source=. --push
# or: create an empty repo on github.com, then
#   git remote add origin <your-repo-url> && git push -u origin main
```

## 1. Neon (Postgres)

1. [neon.tech](https://neon.tech) → New Project → any region close to your
   Render region.
2. On the project dashboard, **Connect** → copy the connection string
   ("Pooled connection" is fine). It looks like:
   `postgresql://user:password@ep-xxxx-pooler.region.aws.neon.tech/routeforge?sslmode=require`
3. Save it — this becomes `DATABASE_URL` in step 3.

Schema is applied automatically on deploy (see the backend's
`preDeployCommand` in `render.yaml`), so no manual migration step is needed.

## 2. Upstash (Redis)

1. [upstash.com](https://upstash.com) → Create Database → Redis, any region
   close to Render.
2. On the database page, copy the **TLS** connection string — it starts with
   `rediss://` (note the double-s: TLS). This becomes `REDIS_URL`.

Redis is a cache-aside layer here (matrix + geocode caching) — if it's ever
briefly unreachable the app degrades gracefully rather than failing
requests, so there's no strict ordering requirement between this and the
other steps.

## 3. Render (backend + optimize-service)

The repo includes `render.yaml`, so both services deploy together as a
Blueprint:

1. [render.com](https://dashboard.render.com) → New → **Blueprint** → connect
   your GitHub repo → Render reads `render.yaml` and proposes both services.
2. Before applying, you'll be prompted for the env vars marked `sync: false`:
   - `routeforge-backend` → `DATABASE_URL` (from Neon, step 1)
   - `routeforge-backend` → `REDIS_URL` (from Upstash, step 2)
   - `routeforge-backend` → `CORS_ORIGIN` — leave as `http://localhost:5173`
     for now; you'll update it to the real Vercel URL in step 5.
   - `JWT_SECRET` is auto-generated by the blueprint (`generateValue: true`)
     — no action needed.
3. Apply. Render builds both Dockerfiles, runs the Postgres migration as a
   pre-deploy step on the backend, then starts both services.
   `routeforge-optimize-service` is a **private service** — no public URL,
   only reachable from the backend over Render's internal network — which is
   correct, since nothing external should call the solver directly.
4. Once live, copy the backend's public URL (something like
   `https://routeforge-backend.onrender.com`) — you'll need it in step 4.

If you'd rather click through the dashboard instead of using the blueprint,
create two services manually: a **Private Service** from
`optimize-service/Dockerfile` on port 8000, and a **Web Service** from
`backend/Dockerfile`, with `OPTIMIZE_SERVICE_URL` on the backend pointing at
`http://<optimize-service-name>:8000`.

## 4. Vercel (frontend)

1. [vercel.com](https://vercel.com) → Add New → Project → import the repo.
2. Set **Root Directory** to `frontend`. Vercel auto-detects the Vite
   framework preset; the included `frontend/vercel.json` handles SPA
   client-side routing (react-router) so deep links/refreshes don't 404.
3. Add an environment variable:
   `VITE_API_BASE_URL = https://routeforge-backend.onrender.com/api`
   (your real Render backend URL from step 3, with `/api` appended).
4. Deploy. Copy the resulting Vercel URL (e.g.
   `https://routeforge.vercel.app`).

## 5. Close the loop: CORS

Go back to Render → `routeforge-backend` → Environment → set `CORS_ORIGIN`
to your real Vercel URL from step 4 (e.g. `https://routeforge.vercel.app`,
no trailing slash). Save — Render redeploys automatically.

## 6. Verify

```bash
curl https://routeforge-backend.onrender.com/api/health
curl https://routeforge-backend.onrender.com/api/health/ready   # checks postgres + redis
```

Then open the Vercel URL, register a user, load the demo route, and hit
Optimize — this exercises the full chain: Vercel → Render backend → Neon +
Upstash → Render optimize-service → OSRM's public demo server.

## Notes / gotchas

- **Render free/starter services spin down when idle** and take ~30–60s to
  wake on the next request — the first optimize call after inactivity will
  be slow. Fine for a portfolio demo; upgrade the plan if you need it always
  warm.
- **OSRM/Nominatim** are the public demo servers (per the original design —
  self-hosting was explicitly out of scope for v1). They're rate-limited and
  not meant for heavy production traffic, which is fine for a demo but worth
  knowing about.
- **Neon's pooled connection string** is recommended over the direct one
  since Render's free/starter plans can otherwise exhaust Neon's connection
  limit under load.
- If you rotate `JWT_SECRET` on Render, all existing logged-in sessions are
  invalidated (expected — it's what the secret is for).
